# Сериализация/десериализация модели: замер (16.10.2026)

Вопрос: можно ли ускорить Ferronit за счёт оптимизации сериализации/десериализации модели.
Ответ, коротко: модель уже на полу, весь её вклад в запрос — 6–10% req/s; настоящий рычаг —
убрать Python из пути данных (JSON собирает PostgreSQL): ×1,7 на 100 строках и ×3,1 на 1000.

Метод: `bench/serdes_bench/` — один granian (1 воркер), одна база, `ab -c 50 -k`, все варианты
в одном окне (раунды чередуются, см. `interleave_ab.py`), тело ответа у всех вариантов
побайтно одинаковое (md5 сверяется в `run_ab.sh`: 5 286 байт на limit=100). Маршрут
`/rows?limit=N`, таблица `bench_rows` = 1000 строк (id, name, email); различается только
сборка ответа.

## req/s (interleaved, медиана 5 раундов, в раунде лучшее из 3)

| вариант | limit=100 | limit=1000 | что это |
|---|---|---|---|
| framework (как сейчас) | 7 349 | 1 856 | msgspec + экранирование HTML |
| cached | 7 814 (×1,06) | 2 041 (×1,10) | сериализация модели снята совсем — потолок для ser/deser |
| jsonsql | **12 650 (×1,72)** | **5 819 (×3,14)** | JSON собирает PostgreSQL (`string_agg(row_to_json(...))`) |
| noescape | 7 591 (×1,03) | 1 990 (×1,07) | `_escape_html` выключен |

## Микро: цена фаз, µs на запрос (та же таблица, 3 колонки)

## CPU на запрос под нагрузкой (мкс; сервер — процесс приложения, PG — cgroup контейнера)

| вариант | limit=100: сервер / PG | limit=1000: сервер / PG |
|---|---|---|
| framework | 158,8 / 106,4 | 585,0 / 353,5 |
| cached | 136,2 / 100,2 | 502,5 / 320,3 |
| jsonsql | 100,0 / 161,6 | 222,5 / 1 216,1 |
| rust | 201,2 / 119,3 | 812,5 / 383,4 |

`jsonsql` не экономит CPU (на 1000 строках суммарно ×1,5 больше), а переносит работу из одного
Python-процесса в 16 параллельных бэкендов PostgreSQL — поэтому и выигрывает по req/s.

## Что проверено и отклонено

- `array_like=True` у модели — на сборку не влияет (0,130 против 0,130 мкс/строку).
- `gc=False` — −7% на сборке (0,121 против 0,130 мкс/строку), но снимает объекты с учёта GC
  (циклы через связи потекут) — не стоит 1% запроса.
- `__new__` + прямая запись слотов — msgspec запрещает (`cannot create 'Wide' instances`),
  `__init__` у Struct-модели типы и так не валидирует (проверено `Wide("x", …)` → принимает).
- Пропуск `_escape_html` по проверке «есть ли `<`/`>`/`&`» — экономит 1,9 мкс на 55 КБ, на req/s
  не видно (`noescape` в шуме) — не стоит правки.
- `msgspec` для одиночного dataclass вместо Rust — ×4,7 на этой ветке, но ветка применяется к
  одному объекту (≈0,7 мкс) — не стоит риска смены порядка.

## Грабли стенда

- Микромерка в одном процессе на Python 3.14 даёт разброс до 10× между прогонами (адаптация/JIT):
  мерить interleave-ом в одном прогоне, а не «до/после» отдельными запусками.
- `asyncpg.Record` нельзя превратить в модель через `record_class`: asyncpg требует подкласс
  `protocol.Record` без своего `__new__`/`__init__` (`_check_record_class`).
- `json_agg` вставляет разделители `", \n "` (+3 байта на строку) — для побайтного паритета
  нужен `string_agg(row_to_json(t)::text, ',')`.
