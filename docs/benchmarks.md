# Бенчмарки

Методика фиксирована: **только ApacheBench** (`ab -n N -c 50 -k`). Python-клиенты
(httpx/asyncio) упираются в ~3.7k req/s независимо от сервера — меряют клиент, а не
фреймворк. Все приложения — на одном сервере, 1 воркер, keep-alive. Полный стенд:
`bench/api_bench.py`.

**Память меряется как PSS** (`smaps_rollup` по дереву процессов сервера): RSS суммирует общие
страницы (libpython, `.so` драйверов, бинарь сервера) в каждом процессе заново, из-за чего у
granian «память на воркер» выходила вдвое больше реальной — на 1 воркер три процесса
(supervisor + helper + worker) давали 106 МБ RSS против 64 МБ PSS, на 10 воркерах 545 против 278.

**Прогон разбит на независимые стадии-проверки** (`ping`, `jwt`, `rows1`, `rows20`, `rows50`,
`rows100`, `rows1000`, `insert`, `update`, `upsert`, `delete` + опциональные `update-spread`,
`upsert-spread` — те же записи, но `id` выбирает сервер, чтобы снять эффект блокировки одной
строки). К каждой стадии с БД дополнительно снимается эталон `pgbench` (тот же оператор без
фреймворка) — см. «Потолок самой БД».: каждая стадия — свой замер по
всем приложениям, свой `bench/results/stage-<имя>.json` и своя диаграмма
`docs/img/charts/stage-<имя>.png`. На диаграммах подпись каждого бара — фреймворк **и слой
доступа**: ORM (SQLAlchemy ORM, GORM, ent, Django ORM), SQL builder (Ferronit `rawmodel` — запрос
строится по модели, и строки маппятся в `Model`; SQLAlchemy Core) или «raw SQL → structs»
(ручные запросы через драйвер, без слоя моделей). У `ferronit-pipeline` в подписи отдельно
указана надбавка `+ aggregate → DTO`. Гипотезу можно проверять одной стадией
(`BENCH_STAGES=rows20`, ~2 минуты), а не полным прогоном.

Внутри стадии раунд — «каждое приложение по одному разу», `BENCH_RUNS=3` раунда, берётся
лучшее: дрейф машины внутри раунда затрагивает всех одинаково, поэтому соотношения сходятся,
а абсолюты между сессиями шумят ±2–3%. Порядок приложений в соседних раундах **чередуется**
(вперёд/назад): иначе приложение с фиксированной первой позицией систематически меряется на
«холодной» машине — это было видно по `ferronit` и `ferronit-pipeline`, у которых на `/ping`
код идентичен. Стадии `mem1`/`mem10` включаются `BENCH_MEMORY=1`. Сводная диаграмма по всем стадиям —
`docs/img/charts/bench-ferronit-baseline.*`. **Базовая линия в измерениях — `ferronit-pipeline`**
(полный DDD-путь: порт → адаптер → агрегат → DTO), `×1` на всех диаграммах и в консоли; остальные
приложения, включая тонкий вариант Ferronit, показаны относительно него. Go выключается `BENCH_NO_GO=1`, выбор приложений —
`BENCH_APPS=ferronit,go-pgx`.

**Основной конкурент — BlackSheep** (ближайший соперник по маршрутизации);
Litestar/FastAPI/Django — дополнительные точки отсчёта.

`ab -c 50 -k`, req/s:

|---|---|---|---|---|---|---|---|---|---|---|---|
| 123 548 | 122 475 | 83 685 | 36 140 | 18 371 | 1 605 | **204 922** | 194 466 | 110 656 | 113 235 | 111 207 | 108 710 |

Ferronit (RSGI) на чистом роутинге быстрее BlackSheep в ~1.48×, Litestar в ~3.4×, FastAPI в ~6.7×,

Впереди только Rust: **Axum ×1.66 и Actix Web ×1.57 к Ferronit** (×1.67/×1.59 к базовой линии

чередуется.

**История ping:** 109 664 (31.10) → 93 423 (просадка) → 121 217 → 123 548 (после возврата
ленивых заголовков; полный прогон 02.11).
Просадка была не от нагрузки (Go-стек все сессии держится на 107–112k): фикс RSGI-заголовков
сначала дёргал `set_headers` (конвертация строк в байты + копия в Rust) на **каждом** запросе,
хотя заголовки большинству маршрутов не нужны. Теперь заголовки нормализуются лениво,
`get_header()` сканирует сырой список в Python (без Rust и без dict), а при мелком теле
`accept-encoding` для gzip даже не читается.

## GET /me — JWT-аутентификация

Реалистичный защищённый эндпоинт: `GET /me` с `Authorization: Bearer <HS256-JWT>`. Секрет,
алгоритм и claims (`sub`, `role`, `exp`) одинаковые во всех стеках; токен минтит стенд (PyJWT),
секрет уходит в приложения через `BENCH_JWT_SECRET`. Проверка встроена **идиоматичным для стека
механизмом**, — поэтому разница и есть цена auth-обвязки:

| Стек | Механизм проверки | Библиотека |
|---|---|---|
| Ferronit | `app.use(...)` middleware + `ContextVar` для claims | PyJWT |
| BlackSheep | `app.middlewares` + claims в `request.scope` | PyJWT |
| Litestar | guard (`guards=[jwt_guard]`) + `connection.state` | PyJWT |
| FastAPI | `Depends(current_claims)` + `Header` | PyJWT |
| Django | middleware (`MIDDLEWARE`) + `request.jwt_claims` | PyJWT |
| Axum / Actix | экстрактор (`FromRequestParts` / `FromRequest`) | `jsonwebtoken` |
| Go (все 4) | `authMiddleware` + `context.WithValue` | `golang-jwt/jwt/v5` |

Перед замером стадия **проверяет контракт у каждого приложения**: 200 с валидным токеном и 401
без него (иначе сломанная авторизация померилась бы как «быстрый 401»). `ab -c 50 -k`,
10 000 запросов, 3 раунда, одна сессия (`2026-11-02`, вместе с `ping`), req/s; `+мкс` — цена
аутентификации относительно того же приложения на `ping` из той же сессии:

| Приложение | ping, req/s | /me (JWT), req/s | +мкс на запрос |
|---|---:|---:|---:|
| Rust Actix | 194 466 | **164 274** | 0,9 |
| Rust Axum | 204 922 | 162 004 | 1,3 |
| Go sqlx | 113 235 | 67 806 | 5,9 |
| Go pgx | 110 656 | 67 259 | 5,8 |
| Go ent | 108 710 | 66 595 | 5,8 |
| Go GORM | 111 207 | 65 713 | 6,2 |
| Ferronit (RSGI) | 123 548 | 24 186 | 33,3 |
| ferronit-pipeline | 122 475 | 23 802 | 33,8 |
| BlackSheep | 83 685 | 23 793 | 30,1 |
| Litestar | 36 140 | 5 771 | 145,6 |
| FastAPI | 18 371 | 4 691 | 158,7 |
| Django | 1 605 | 1 352 | 116,5 |

- **В Python доминирует сам PyJWT, а не фреймворк:** `jwt.decode` (HS256 + base64 + JSON + claims)
  стоит 18,1 мкс на вызов, а под 50 конкурентными задачами — ~29 мкс; ручная проверка на
  `hmac`/`hashlib`/`json` (то же самое, без валидации iss/aud) — 3,6 мкс. На этом фоне
  обвязка Ferronit (middleware + claims + разбор заголовков) — **+1,3 мкс** к проверке внутри
  хендлера. Отсюда и разрыв с Go (×3,1) и Rust (×7,3–7,5): у них JWT-библиотеки компилируемые.
- **Среди Python-стеков Ferronit делит первое место с BlackSheep** (24 186 против 23 793, ×4,2
  к Litestar): после перехода на ленивые заголовки и `get_header()` разрыв в 12% исчез —
  в этом сценарии маппинг не участвует, и `ferronit-pipeline` отстаёт на 3% только за счёт
  шума.
- **Litestar и FastAPI платят за механизм, а не за криптографию:** guard в Litestar добавляет
  ~150 мкс, `Depends` + `Header` в FastAPI — ~160 мкс (pydantic-валидация параметра на каждый
  запрос), это в 5–6 раз больше самой проверки токена.
- **Django:** JWT почти не виден на фоне 612 мкс базового запроса — там доминирует sync-ORM/
  ASGI-мост, поэтому `+103 мкс` выглядят «дешёвыми» только относительно его же ping.
- **Найден и убран налог на gzip.** Профиль по RSGI показал: если клиент присылает
  `Accept-Encoding: gzip`, каждый ответ уходил в zlib — фиксированная цена ~42 мкс, причём
  11-байтное тело вырастало до 31 Б. На `/me` это дало бы ~11k вместо ~20k req/s. Теперь тела
  меньше `gzip_min_size` (500 Б по умолчанию) не сжимаются; под `ab -H 'Accept-Encoding: gzip'`
  `/me` даёт те же ~20k, что и без заголовка. Замеры на `ab` этот путь не видели: ApacheBench
  `Accept-Encoding` не шлёт, а браузеры и `httpx`/`requests` — шлют.
- Стадия нашла **реальный баг Ferronit на RSGI**: `_rsgi_request` отдавал заголовки строками,
  а `Request` ждал байты; конвертация падала и глушилась, поэтому `request.headers`,
  `get_header()` и куки на RSGI были пустыми — любая аутентификация отдавала 401. Исправлено
  (`ferronit/core/app.py`, `request.py`), регрессия закреплена `tests/test_rsgi.py`.

req/s, все приложения в одной сессии:

|---|---|---|---|---|---|---|---|---|---|---|---|---|

- **Rust впереди всех** (×1,2–2,1 к базовой линии, ×1,0–1,4 к Go pgx): Axum/Actix на `sqlx` +
  `serde_json` почти не платят за строку; на `limit=1000` Ferronit уже почти догнал Axum
  (896 против 914), а Actix по-прежнему быстрее Go (1 030 против 830).
- **Go впереди Ferronit на малых лимитах, но разрыв сжался:** ×1,91 на `limit=1`, ×1,20 на 20,
  ×1,06 на 50 и ×1,05 на 100; на `limit=1000` Ferronit впереди (896 против 830). До
  оптимизации возврата соединения в пул было ×2,87 / ×1,48 / ×1,30 / ×1,21 — см.
  «Малые выборки: цена возврата соединения в пул».
- FastAPI (SQLAlchemy ORM) отстаёт от Ferronit в ×8,1–10,8, Django (sync ORM) — 376–493 req/s.
- `ferronit-pipeline` — базовая линия всех замеров. Относительно тонкого Ferronit он стоит
  2–16% req/s на чтении (`rows1` ×0,98, `rows20`–`rows1000` ×0,92–0,84); на `rows1` это в
  пределах шума сессии (±2%), а на записи разницы нет (×1,00) — это и есть измеренная
  цена маппинга «модель → агрегат → DTO».
- **Litestar меряется на SQLAlchemy Core** (как BlackSheep), чтобы сравнение было по фреймворку, а
  не по слою доступа: на голом asyncpg он был быстрее Ferronit на 15–25%, но это заслуга драйвера.

### Малые выборки: цена возврата соединения в пул (01.11.2026)

`limit=1` и `limit=20` упирались не в PostgreSQL (потолок `pgbench` — ×13–16 выше) и не в
JSON, а в **фиксированную цену запроса**. Разбор по слоям (in-process, 50 конкурентных задач,
CPU процесса на запрос) показал, где она сидела:

| Слой (запрос `SELECT … LIMIT 1`) | было, мкс | стало, мкс |
|---|---:|---:|
| `pool.acquire()` + `release()` | 43 | 10 |
| — из них `reset`-запрос asyncpg | 30 | 0 |
| `conn.fetch()` (драйвер + декод) | 25 | 25 |
| UoW + репозиторий модели | 20 | 7 |
| ASGI-диспетчер + ответ | 5 | 5 |
| **итого `/rows?limit=1`** | **95** | **54** |

Что изменено в слое данных:

1. **Возврат соединения в пул без `RESET ALL`.** asyncpg на каждом `release()` выполнял
   `SELECT pg_advisory_unlock_all(); CLOSE ALL; UNLISTEN *; RESET ALL;` — лишний round-trip
   (~30 мкс CPU + сетевая задержка) на каждый запрос. Теперь по умолчанию откатывается только
   открытая транзакция (как в Go `pgx` и Rust `sqlx`), а полный сброс сессии включается
   `create_pool(..., reset_on_release=True)`, если хендлеры меняют состояние сессии
   (`SET`, temp-таблицы, `LISTEN`, advisory-локи).
2. **Таймер простоя пула не тикает:** `max_inactive_connection_lifetime=0` — asyncpg иначе
   создаёт и отменяет `TimerHandle` на каждый acquire/release (~3,5 мкс), а закрывает он только
   соединения сверх `min_size`.
3. **SQL репозитория компилируется раз на модель, а не на запрос:** `RawModelRepository`
   создаётся в каждой единице работы, и самый дорогой statement (`SELECT` по pk со связями)
   пересобирался каждый раз (~3 мкс); теперь он в `lru_cache` вместе с остальными.

HTTP-эффект (та же сессия, 3 раунда, все стеки — таблица выше): `rows1` 11 709 → **16 081**
(+37%), `rows20` 9 123 → **12 486** (+37%), `rows50` 6 589 → 8 593 (+30%),
`rows100` 4 633 → **5 499** (+19%), `rows1000` 840 → 910 (+8%). На больших лимитах выигрыш
меньше: там доминирует декодирование дат, а не фиксированная цена запроса. `rows1` — самый
шумный замер (±10–15% между сессиями), его стоит читать как «потолок издержек фреймворка».

- UPDATE/UPSERT — 0,8–1,1k: доминирует диск, а UPDATE вдобавок бьёт **в одну и ту же строку**
  `id=1` (50 клиентов сериализуются на её блокировке), поэтому он медленнее DELETE.
- **FastAPI на UPDATE больше не выбивается вперёд:** раньше он показывал 1 400–1 500 req/s, потому
  что ORM-сессия меняла атрибуты на те же значения и dirty-tracking не отправлял UPDATE
  (по `pg_stat` — 1 запрос на 2 000). Теперь в стенде Core-выражение `sa_update(...).returning(...)`,
  каждый запрос пишет строку, и FastAPI упал до 667 req/s (×0,73 к базовой линии).
- **DELETE меряется по-настоящему:** `ab` бьёт один URL, поэтому удаляем строку с минимальным
  `id` через `… ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED` — `SKIP LOCKED` разводит 50
  конкурентных запросов по разным строкам, и каждый запрос удаляет живую строку (проверено:
  4 000 предзасеянных строк, 3 000 запросов, `pg_stat` показывает 3 000 удалений). Раньше
  DELETE бил в `id=1` и после первого запроса был no-op (30–35k req/s у Go/Rust) — это число
  показывало цену пустого запроса, а не удаления; теперь DELETE сопоставим с INSERT.
- CPU-цена этих же сценариев (сервер/PG/клиент) — в разделе «CPU под HTTP-нагрузкой».

## Запросы к БД в процессе: Ferronit против SQLAlchemy (окт 2026)

`bench/queries_vs_sqlalchemy.py` — не через HTTP: один процесс, один event loop, **1 клиент**,

пересоздаётся, autovacuum на ней выключен, перед каждой операцией `CHECKPOINT` + пауза (см.

|---|---|---|---|---|---|

| list (100 строк) | 4 490 | 4 168 | 2 154 | 1 343 | **4 959** |

### CPU: цена слоя живёт в клиенте (окт 2026)

Тот же стенд считает CPU процесса клиента (`time.process_time()`) и CPU сервера
(по cgroup контейнера, `bench/_probe_pg_cpu.py`), мкс на запрос:

| Операция | Ferronit rawmodel | SQLAlchemy Core | SQLAlchemy ORM | asyncpg |
|---|---|---|---|---|
| get 1 строки | 76 + 24 | 265 + 28 | 330 + 28 | 64 + 20 |
| list 100 строк | 167 + 43 | 392 + 39 | 613 + 55 | 140 + 40 |
| INSERT | 137 + 91 | 345 + 99 | 433 + 99 | 115 + 93 |

(первое число — CPU клиента, второе — PostgreSQL.)

- **На стороне базы цена запроса одинакова у всех слоёв** (24–28 мкс на точечное чтение,
  40–55 на 100 строк, ~95 на вставку) — вся разница слоёв сидит в Python клиента.
  У ORM 92% CPU запроса — это сам ORM (330 из 358 мкс).
- **Занятость ядра на 1 клиенте:** чтение — Ferronit 0,64–0,75 ядра, SQLAlchemy 0,82–0,86;
  запись — 0,11–0,13 против 0,23–0,37 (остальное клиент ждёт диск).
- **Потолок одного ядра** (1e6 / мкс CPU): get 1 строки — 13 242 у модели против 3 770 (Core)
  и 3 030 (ORM); list 100 — 5 989 против 2 552 и 1 633; INSERT — 7 286 против 2 901 и 2 309.
  То есть при росте нагрузки SQLAlchemy упирается в CPU в **2–4,4 раза раньше**, чем слой
  Ferronit, а на записи — раньше, чем кончится диск (у ORM потолок 1 633–3 030).

Грабли замера (все проверены прямым прогоном):

1. **Фоновый autovacuum роняет записи втрое** (930 → 330 запросов/с): прогоны оставляют десятки
   тысяч мёртвых версий, vacuum стартует по 20%-порогу и ест I/O прямо во время замера.
   Стенд выключает autovacuum на `bench_rows` и возвращает настройку в конце.
2. **Остаточный I/O после тяжёлой фазы** — тот же эффект ×3 на **первом** замере следующего
   блока (319 против 939 запросов/с). Лечится `CHECKPOINT` + пауза 5 с перед каждой операцией;
   без паузы последние операции матрицы (upsert/delete) выглядят сломанными.
3. **ORM не отправляет UPDATE, если значение не изменилось** (dirty-tracking): в первом варианте
   стенда UPDATE писал ту же строку и то же значение, SQLAlchemy не слала запрос вовсе — 1 954
   запросов/с фейка против 623 реальных. Значение UPDATE/UPSERT обязано меняться каждую итерацию.
   В стадийном стенде это ловилось заново: FastAPI-вариант менял атрибуты ORM-модели, и при
   `ab` (один и тот же body) UPDATE не уходил в базу — 1 реальный запрос на 2 000. Проверка —
   `n_tup_upd` из `pg_stat_user_tables` до/после стадии; лечение — `sa_update(...).returning(...)`.
4. **Аннотации `Mapped[...]` не резолвятся, если модель объявлена внутри функции** — только на
   уровне модуля.

### Цена декодирования дат (29.10.2026)

Схема стенда с 29.10 содержит `timestamptz`/`date`/`interval` — это первые типы, которые asyncpg
декодирует в **объекты Python** (datetime/date/timedelta), а не в int/str. Два отдельных зонда:

`bench/datetime_decode_bench.py` — один и тот же `SELECT … LIMIT 1000` с тремя наборами колонок
(1 клиент, 300 итераций, лучшее из 3):

| набор колонок | req/s | CPU/запрос, мкс | CPU/строка, мкс |
|---|---|---|---|
| `datetime` (created_at, birthday, ttl) | 1 233 | 691 | 0,691 |
| `plain` (id, name, email) | **3 643** | **220** | **0,220** |
| `all` (все шесть) | 1 081 | 799 | 0,799 |

- **Даты — 59% CPU запроса на 1000 строк:** 691 − 220 = 471 мкс (0,47 мкс на строку) при трёх
  datetime-колонках. `plain` служит контролем: там эффекта быть не должно, и он упирается в int+2 text.
- **В модели эти же даты добавляют только 0,12 мкс на строку:** `bench/list_rows_bench.py`
  (LIMIT 1000, три слоя поверх одного драйвера, req/s / CPU на строку):

  | слой | req/s | CPU/запрос, мкс | CPU/строка, мкс |
  |---|---|---|---|
  | ferronit-rawmodel | 938 | 896 | 0,896 |
  | ferronit-rawdb | 677 | 1 224 | 1,224 |
  | asyncpg (дно) | **1 037** | **772** | **0,772** |

  То есть модель отстаёт от сырого asyncpg на 10% req/s (+0,12 мкс/строку), `rawdb` без модели —
  на 35% (+0,45 мкс/строку: сборка `dict`-строк и работа с `Record` туда-обратно).
- **Вывод для слоя:** платить за даты приходится в драйвере и в любом случае на всех слоях,
  а накладные расходы Ferronit (0,12 мкс/строку) в 4 раза меньше цены самих дат — ускорять
  datetime-кодек в обход asyncpg смысла нет, пока в ответе есть даты; выигрыш там ограничен
  потолком `asyncpg` на `plain` (3 643 req/s при 1 233 на датах).
- **Стоимость видна и в общих числах:** `list_100` в in-process стенде был 6 723 req/s на трёх
  колонках и стал 4 490 на шести (×0,67), `limit=1000` под HTTP — 1 089 (22.10) → 853 req/s (30.10, та же сессия с Go).

## Запись: чем разгоняется PostgreSQL (окт 2026)

Тот же одиночный `INSERT` одной строки в одной транзакции (`bench/_probe_write_tuning.py`,

| Режим | записей/с | к baseline |
|---|---|---|
| baseline: `fsync=on`, `synchronous_commit=on`, 1 клиент | 953–989 | ×1 |
| `synchronous_commit=off` (per-session), 1 клиент | **20 369–24 064** | **×23** |
| `fsync=off` (ALTER SYSTEM), 1 клиент | 18 615 | ×19 |
| `full_page_writes=off`, 1 клиент | 1 002 | ×1,03 |
| UNLOGGED-таблица, 1 клиент | 19 385 | ×20 |
| 50 клиентов, `fsync=on` (групповой коммит) | 18 637 | ×19 |
| 50 клиентов, `synchronous_commit=off` | 70 190 | ×72 |
| batch 10 строк в одной транзакции | 8 956 | ×9 |
| batch 100 строк в одной транзакции | 67 986 | ×70 |
| batch 100 + `synchronous_commit=off` | **464 662** | **×479** |
| 50 клиентов, `commit_delay=1000` (групповой коммит вручную) | 14 353 | ×15 — **хуже** |
| 50 клиентов, `wal_sync_method=open_datasync` | 18 701 | ×19 (в пределах шума) |
| 50 клиентов, `wal_sync_method=fsync` | 8 060 | **×8,3 — хуже в 2,4 раза** |

(последние три — `bench/_probe_write_tuning3.py`, сравнение с baseline 50 клиентов = 19 603–19 894)

Что из этого следует:

- **Главный рычаг — не настройка, а отказ ждать fsync на каждый коммит.** Один и тот же
  `INSERT` идёт 970 записей/с при `synchronous_commit=on` и ~22 000 при `off` — то есть
  ~1 мс на транзакцию была платой за fsync, а не за работу базы.
- **Групповой коммит бесплатен по надёжности:** 50 параллельных клиентов дают ×19 на тех же
  настройках — PostgreSQL объединяет fsync десятков транзакций в один.
- **Батчинг сильнее любой настройки сервера:** 100 строк в одной транзакции дают 68 000
  записей/с (×70), а вместе с `synchronous_commit=off` — 464 662 (×479).
- **`full_page_writes=off` не дал ничего** (1 002 против 970) — рычаг не из этой задачи.
- **`commit_delay` вредит:** при живом групповом коммите ручная задержка только добавляет сон
  (−27%); `wal_sync_method=fsync` (вместо дефолтного `fdatasync`) режет запись в 2,4 раза.
  Серверные ручки синхронизации уже выбраны правильно, крутить их нечего.
- `fsync=off` (18 615) упирается примерно туда же, где 50 клиентов с групповым коммитом
  (18 637): потолок держит клиентский процесс и writeback ОС, а не fsync.

Риски (обязательно называть рядом с числом):

- `synchronous_commit=off` — при краше ОС или питания теряются транзакции за последнее окно
  записи WAL (~`wal_writer_delay` = 200 мс); при падении **только процесса** PostgreSQL потерь нет.
- `fsync=off` — риск необратимой порчи кластера даже при краше ОС; только для тестовых стендов.
- UNLOGGED-таблица после краша пуста — годится для пересчитываемых данных (кэш, staging).
- batch меняет форму запросов (одна транзакция на N строк), а не сервер: выигрыш берётся из
  числа fsync, а не из настроек.

### Батчинг и сохранность данных (проверено опытом, не рассуждением)

`bench/_probe_batch_durability.py`, `_probe_batch_limits.py`, `_probe_copy.py`:

| Опыт | Результат |
|---|---|
| батч 100 строк, конфликт UNIQUE на 50-й | в таблице **0** новых строк — батч атомарен, откатился целиком |
| батч 500 строк, `synchronous_commit=on`, затем SIGKILL контейнера и старт | **500 строк на месте** — durability не потеряна |
| то же с `synchronous_commit=off` | **0 строк** — все 500 потеряны (WAL не был записан даже в файл ОС) |
| предельный размер батча параметрами (asyncpg) | 32 600 параметров — ок, 32 800 — отказ; при 2 колонках это **16 383 строки**, при 3 — ~10 922 |
| запись 10 000 строк: multi-row `INSERT` против `COPY` | 360 633 против **874 958** строк/с (×2,4) |

Практические следствия:

- **Батчинг сам по себе сохранность не ослабляет:** `COMMIT` по-прежнему ждёт fsync, просто один
  fsync обслуживает N строк (отсюда и цена: батч 100 при `sync=on` — 68 000 записей/с против
  464 662 при `off`).
- **Что батч меняет — семантику:** всё-или-ничего на весь батч (ошибка в одной строке откатывает
  остальные), дольше держатся блокировки, и ответ клиенту нельзя отдавать раньше коммита.
  Лечится `ON CONFLICT DO NOTHING`/разбиением на чанки и retry.
- **Сохранять данные ослабляют не батч, а режимы:** `synchronous_commit=off` (потеря закоммиченного
  подтверждена SIGKILL-опытом), `fsync=off`, UNLOGGED.
- **Размер чанка ограничен клиентом:** у asyncpg потолок 32 767 параметров на запрос (ниже
  серверных 65 535) — то есть для 3 колонок chunk ≤ ~10 900 строк; больше — чанками (COPY отложен
  решением 16.10.2026, см. раздел ниже).
- **Безопасность в смысле инъекций:** батч параметризуется (`$1…$N`), добавления риска нет;
  склейка значений в текст SQL (как в быстрых пробниках скорости) в приложении недопустима.

### COPY: что это в наших числах (проверено, **отложено**)

> **Решение Дениса 16.10.2026: сейчас COPY не берём.** Раздел оставлен как справка по числам и
> семантике — в план и в слой данных он не идёт; рекомендации ниже без акцента на COPY.

Речь о **протокольном `COPY … FROM STDIN`** (массовая загрузка потоком), а не о серверном
`COPY … FROM '/файл'` (тот читает файл на сервере и требует прав суперпользователя). В asyncpg это
`copy_records_to_table(table, *, records, columns=[…])`, в psycopg3 — `cursor.copy()`; SQL-текстом
через обычный `execute` его не сделать.

`bench/_probe_copy.py`, `_probe_copy_semantics.py`, `_probe_copy_transaction.py`:

| Что проверяли | Результат |
|---|---|
| 10 000 строк: multi-row `INSERT` против COPY | 360 633 против **874 958** строк/с (×2,4) |
| участие в транзакции (исключение внутри `transaction()`) | строк после отката **0** — COPY откатывается вместе с UoW |
| то же между явными `BEGIN`/`ROLLBACK` | **0** — откат работает |
| `INSERT` + COPY в одной транзакции | **11** строк (обе операции вместе) — комбинируется |
| конфликт UNIQUE внутри пачки | ошибка, **ни одна** строка пачки не прилетела |
| `serial`-колонка и триггеры | id заполнены (1..100), AFTER-INSERT-триггеров сработало **100 из 100** |
| `RETURNING` у COPY | `PostgresSyntaxError` — у COPY его нет, сгенерированные id не вернуть |

Ограничения: нет `RETURNING`, нет `ON CONFLICT` (конфликт = ошибка всей пачки), правила (rules) не
выполняются. Поэтому пакетный **upsert** делается multi-row `INSERT … ON CONFLICT … DO UPDATE`, а
COPY — для чистых вставок большими объёмами. В нашем слое COPY пока **не используется**
(`ferronit/contrib` — 0 вхождений), то есть для применения нужно сначала добавить его в слой данных.

Грабли харнесса: `async with conn.transaction():` без исключения делает **COMMIT**, а не откат —
первый прогон я прочитал как «COPY не откатывается», хотя отката в том сценарии и не было
(перепроверено отдельным пробником с контролем на обычном `INSERT`).

## Сериализация/десериализация модели: где предел (окт 2026, `bench/serdes_bench/`)

Все варианты читают одну таблицу тем же путём (фреймворковый `uow.model(...).list()`) и отдают
**побайтно одинаковое тело** (`run_ab.sh` сверяет md5: 5 286 байт на `limit=100`); различается
только сборка ответа. Один granian (1 воркер), одна база, `ab -c 50 -k`, варианты чередуются по
раундам (`interleave_ab.py`), медиана 5 раундов, req/s:

| вариант ответа | limit=100 | limit=1000 |
|---|---|---|
| msgspec + экранирование (как сейчас) | 7 349 | 1 856 |
| сериализация снята совсем (`cached`) | 7 814 (×1,06) | 2 041 (×1,10) |
| **JSON собирает PostgreSQL** (`jsonsql`) | **12 650 (×1,72)** | **5 819 (×3,14)** |
| `_escape_html` выключен | 7 591 (×1,03) | 1 990 (×1,07) |

Микро-цены тех же фаз (µs на запрос, таблица `id, name, email`):

| фаза | limit=100 | limit=1000 |
|---|---|---|
| `tuple(row)` — потолок обхода строк | 4,66 | 40,74 |
| `dict(row)` | 16,89 | 186,87 |
| `BenchRow(*row)` — модель | 7,67 | 73,32 |
| `msgspec.json.encode` | 3,07 | 26,77 |
| `_escape_html` | 0,26 | 1,91 |
| **итого map+encode+escape** | **11,70** | **102,70** |

Что из этого следует:

- **Сериализация и десериализация модели — не рычаг:** сняв её целиком (`cached`), получаем
  +6% на 100 строках и +10% на 1000, то есть это и есть её полный вклад в req/s.
- **Модель уже быстрее альтернатив на обоих концах:** сборка 7,7 мкс против 16,9 у `dict(row)`
  (×2,2), кодирование моделей 3,1 против 4,4 у dict (×1,4); `json.dumps` — ×5,6.
- **Пропуск экранирования по проверке ничего не даёт** (в шуме), `array_like` не даёт ничего,
  `gc=False` даёт −7% на сборке, но снимает объекты с учёта GC — правки не стоят своего риска.
- **Рычаг — убрать Python из пути данных:** если JSON собирает сама PostgreSQL
  (`string_agg(row_to_json(t)::text, ',')`), это ×1,7–3,1 req/s, причём CPU не экономится
  (суммарно на 1000 строках ×1,5 больше) — выигрыш в том, что работа уходит из одного
  Python-процесса в параллельные бэкенды PostgreSQL. Цена: пути через модели нет (типизированного
  доступа тоже), `row_to_json` — только PostgreSQL.

Подробности, грабли стенда и что проверено-отклонено — `bench/serdes_bench/RESULTS_serdes.md`.
