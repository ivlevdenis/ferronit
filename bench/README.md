# Стенд замеров Ferrox

Здесь лежат скрипты, которыми получены цифры в README. Это **не часть пакета**: черновой
измерительный код, который не линтуется (`ruff` исключает `bench/`) и не попадает в
sdist/Docker-образ. Логика фреймворка от него не зависит.

## Политика: req/s меряем только `ab`

**Единственный источник цифр по HTTP — ApacheBench (`ab`, C-клиент).** Python-клиент
(httpx/asyncio) сам упирается в ~3.5–3.7k req/s независимо от сервера: в этих замерах
измеряется клиент, а не фреймворк. Поэтому httpx-скрипты переехали в `legacy_httpx/`
и **не используются для сравнения** (оставлены как история методов и для отладки).

## Основное

```bash
./bench/run_all_ab.sh                     # вся матрица, ~10 минут, пишет bench/RESULTS_ab.txt
.venv/bin/python bench/ab_bench.py --server uvicorn --routes 50
.venv/bin/python bench/ab_bench.py --server granian  --routes 1000 --requests 20000
.venv/bin/python bench/ab_bench.py --server uvicorn --payload big --requests 3000
```

`ab_bench.py` сам генерирует два одинаковых приложения (Ferrox и FastAPI) с N маршрутами,
поднимает их одним сервером (uvicorn или granian, 1 воркер), греет и меряет по выборке
маршрутов **первый / средний / последний** — так видно, что FastAPI деградирует при росте
таблицы маршрутов, а Ferrox нет. Флаги: `--routes`, `--requests`, `--concurrency`, `--runs`,
`--payload {none,small,medium,big}`, `--no-fastapi`.

| Скрипт | Что мерит |
|---|---|
| `ab_bench.py` | маршрутизация и размер ответа, Ferrox vs FastAPI, uvicorn/granian — **на `ab`** |
| `bench_db.py [granian\|uvicorn]` | SQLite: GET/POST, ORM vs CoreRepository vs FastAPI — **на `ab`** |
| `bench_db_variants.py` | где потолок SQLite: sync sqlite3 / aiosqlite / Core — **на `ab`** |
| `bench_db_pool.py` | пул коннектов против одного: почему пул вредит (GIL) — **на `ab`** |
| `bench_postgres.py [granian\|uvicorn]` | PostgreSQL 18 в Docker: Core vs ORM vs FastAPI — **на `ab`** |
| `micro_bench_db.py`, `micro_bench_json.py`, `micro_bench_response.py`, `micro_bench_model.py` | микрозамеры слоёв (драйвер БД, Rust JSON против json.dumps, сборка ответа json+gzip, маппинг строк dict/модель) — без HTTP |
| `bench_rows.py`, `plot_rows.py` | Ferrox vs Litestar/FastAPI/Django: 1/100/1000 строк из PostgreSQL — **на `ab`**; `plot_rows.py` строит HTML-график |
| `pg_direct.py` | прямой замер PostgreSQL без фреймворка (asyncpg, `SELECT ... LIMIT 100`) |
| `pg_wire.py`, `wire_bench.py` | самодельный клиент по проводу PostgreSQL (SCRAM, простой и расширенный протокол, пайплайн) против asyncpg |
| `profile_db_path.py` | профиль пути через базу: `/ping`, `/asyncpg`, `/raw`, `/core`, `/orm` + разложение по блокам |
| `rust_pg_orm/` | Rust-стенд: `tokio-postgres`, `sqlx`, `SeaORM` (`--mode --op --clients --threads`), плюс HTTP-сервис на axum (`run_http_ab.sh`) |
| `go_pg_orm/` | Go-стенд: `pgx`, `sqlx`, `GORM`, `ent` (`--mode --op --clients`, GOMAXPROCS), плюс HTTP-сервис на net/http (`run_all.sh`, `ab_json.sh`) |
| `prof_*.py` | профилирование горячего пути (`cProfile`) |

## Прямой замер PostgreSQL (окт 2026)

`bench/pg_direct.py` повторяет запрос приложения (`SELECT ... LIMIT 100`), но напрямую через
asyncpg — видно потолок самой базы. Инстанс: `postgres:latest` = **18.6**, дефолтный конфиг
докерного образа (shared_buffers 128 МБ, fsync и synchronous_commit = on), лимитов CPU/памяти
нет, 20 ядер, NVMe. Датасет pgbench — scale 10 (1 млн строк, 157 МБ).

| Замер | Результат |
|---|---|
| pgbench SELECT-only, 1 клиент | 57 473 tps (0.017 мс) |
| pgbench SELECT-only, 50 клиентов / 4 потока | **360 730 tps** (0.139 мс) |
| pgbench SELECT-only, 100 клиентов | 329 086 tps (0.304 мс) |
| pgbench TPC-B (3 чтения + запись + вставка, fsync on), 50 | 3 849 tps (12.99 мс) |

### Лестница доступа к тем же 100 строкам (`SELECT ... LIMIT 100`)

Один и тот же запрос, один Python-процесс, PG 18.6 (`--mode asyncpg|core|orm` в `pg_direct.py`):

| Способ доступа | 10 клиентов | 50 клиентов |
|---|---|---|
| asyncpg (сырой драйвер) | **33 150** запросов/с | 27 603 |
| SQLAlchemy Core (`select(...)` + `mappings()`) | 4 815 | 4 550 |
| SQLAlchemy ORM (`select(User)` + объекты) | 2 708 | 2 639 |

Читается это так: **SQLAlchemy срезает скорость драйвера почти в 7 раз** (33 150 → 4 815),
ORM — ещё в 1,8 раза (4 815 → 2 708), а HTTP-слой Ferrox на одном воркере — ещё в 5 раз
(4 815 → 932–1 132). Восемь воркеров возвращают ×5,3 (до 4 984).

Потолок одного клиентского процесса проверен параллельным запуском: **4 процесса × 10 клиентов
дали 85 491 запрос/с суммарно** (по 20–23 тыс. на процесс) — то есть 33 тыс. ограничены
процессом клиента (GIL/цикл событий), а не драйвером и не сервером. Сама база на простых
SELECT'ах через pgbench уходит за 360 тыс. tps.

**Вывод:** сама база отдаёт тот же запрос **в ~20 раз быстрее**, чем приложение через HTTP
(Ferrox-Core GET /users = 1 132 req/s на том же инстансе). На этой нагрузке узкое место —
Python/HTTP-слой, а не PostgreSQL, и вся разница Core/ORM/FastAPI живёт в нём. Записи в
дефолтном конфиге упираются в диск: 3 849 tps против 360 730 на чтении.

### Почему «по базе» такие низкие цифры (разложение, окт 2026)

Тот же инстанс, granian, `ab -c 50`, `BENCH_WORKERS=1`:

| Что меряем | Значение | На запрос |
|---|---|---|
| `GET /ping` — тот же сервер, без базы (Ferrox-Core) | 83 966 req/s | 12 мкс |
| `GET /users` — SELECT 100 строк (Ferrox-Core) | 932 req/s | 1 073 мкс |
| прямой asyncpg того же SELECT (1 клиент) | 13 929 запросов/с | 72 мкс |
| pgbench на том же инстансе (50 клиентов) | 360 730 tps | 139 мкс |

Значит база — это ~7–13% времени запроса, а остальное Python-обвязка: сессия SQLAlchemy
(checkout соединения из пула), маппинг 100 строк в объекты/словари, сериализация в JSON и
ASGI-путь. Контрольный `/ping` это подтверждает: без базы тот же сервер отдаёт 84 тыс. req/s,
то есть «голый» путь фреймворка стоит 12 мкс — вся стоимость появляется вместе с базой.

Второе подтверждение — масштабирование воркерами (`BENCH_WORKERS=N`, granian):

| Воркеров | `GET /users` Ferrox-Core | `POST /users` Ferrox-Core | `GET /ping` Ferrox-Core |
|---|---|---|---|
| 1 | 932 | 617 | 83 966 |
| 4 | 1 560 | 1 805 | 113 568 |
| 8 | 4 984 | 6 849 | 152 446 |

Путь через базу растёт линейно с числом процессов (932 → 4 984, ×5.3) — типичный CPU-bound
Python, а не ожидание базы (база в это время загружена на единицы процентов от своих
20 000–360 000 запросов/с). Посторонний вывод: на этой нагрузке PostgreSQL-путь в приложении
медленнее SQLite-пути (932 против 2 321 req/s из `bench_db.py`) — это разница драйверов и
транспорта (aiosqlite по файлу против asyncpg через TCP и порт-маппинг Docker), не «скорость
базы».

### Драйверы: asyncpg против psycopg 3 (`--mode asyncpg|psycopg|core|orm|*-psycopg`)

Замеры вперемешку (asyncpg/psycopg по кругу, 3 цикла — чтобы условия были одинаковыми),
тот же запрос `SELECT ... LIMIT 100`, тот же инстанс. Установка для воспроизведения:
`uv pip install --python .venv/bin/python "psycopg[binary,pool]"`.

| Слой | 10 клиентов: asyncpg | 10 клиентов: psycopg 3 | Разница |
|---|---|---|---|
| сырой драйвер | **33 100** запросов/с (p50 0.30 мс) | 21 650 (p50 0.46 мс) | **−34%** |
| SQLAlchemy Core | 4 740 (p50 1.97 мс) | 4 139 (p50 2.39 мс) | −13% |
| SQLAlchemy ORM | 2 750 (p50 3.50 мс) | 2 485 (p50 4.00 мс) | −10% |

При 50 клиентах: сырой asyncpg 27 800 против psycopg 21 630 (−22%).
Круг до базы на `SELECT 1`: asyncpg 27–28 мкс, psycopg 89–288 мкс — у psycopg заметно
дороже Python-обвязка на каждый оператор.

Читается это так: **чем выше слой, тем меньше значит выбор драйвера.** На сыром драйвере
asyncpg быстрее на треть, но под SQLAlchemy разница сжимается до 10–13%, потому что сам
SQLAlchemy ужимает поток в ~7 раз сильнее. Для приложения на SQLAlchemy смысла менять
диалект ради скорости нет; psycopg 3 берут за другое — DB-API-совместимость, единый API
для sync и async, pipeline mode и официальные бинарные колёса.

### ORM на Rust против Python (`bench/rust_pg_orm/`, окт 2026)

Тот же запрос, тот же инстанс PostgreSQL 18.6, 10 клиентов × 1000 запросов. Python — один
процесс asyncio (это аналог одного потока), Rust — `--release`, рантайм tokio на 1 и 8 потоках.

| Слой | Python, 1 процесс | Rust, 1 поток | Rust, 8 потоков |
|---|---|---|---|
| сырой драйвер, чтение | asyncpg **32 869** | tokio-postgres 25 500 | 31 844 |
| запросный слой, чтение | SQLAlchemy Core 4 992 | sqlx 14 714 | 38 001 |
| ORM, чтение | SQLAlchemy ORM **2 732** | SeaORM **13 400** | 33 962 |
| сырой драйвер, запись | asyncpg 4 509 | tokio-postgres 5 169 | 4 827 |
| ORM, запись | SQLAlchemy ORM 2 294 | SeaORM 4 676 | 4 798 |

Числа Rust — медианы трёх прогонов (разброс 3–4 %), Python — из той же сессии.

Что из этого следует:

* **Цена ORM относительно драйвера: в Rust ×1,9, в Python ×12** — в шесть раз меньше.
* **SeaORM против SQLAlchemy ORM: ×4,9** (13 400 против 2 732) на чтении.
* **Сам Rust-драйвер не быстрее Python-драйвера**: tokio-postgres 25 500 против asyncpg 32 869
  в один поток. asyncpg очень хорошо оптимизирован — выигрыш Rust живёт в слоях выше и в потоках.
* **Чтение в Rust масштабируется потоками** (sqlx 14 714 → 38 001), в Python упирается в GIL:
  один процесс = один поток, потолок ~33 тыс.
* **Запись упирается в диск, а не в язык**: 4,5–5,2 тыс. у обоих драйверов, восемь потоков не
  помогают (4 827 против 5 169) — это `fsync`/WAL.

Diesel не проверен: ему нужен `libpq-dev` (`pg_config` и заголовки), которых в системе нет.

### Запросы в БД в Rust: `ferrox.db` (окт 2026)

`ferrox.db.query_json(sql, params)` выполняет запрос в Rust (tokio-postgres через пул
`deadpool-postgres`) и возвращает готовую JSON-строку, поэтому Python не трогает строки —
ни маппинг, ни сериализация под GIL. API: `ferrox.db.connect(dsn, pool_size)` один раз на
старте + `await asyncio.to_thread(ferrox.db.query_json, sql, [])`. Живёт в едином пакете
ferrox как вложенный модуль `ferrox._core.db`.

Замер после перехода на `deadpool` + `prepare_cached` (granian, 1 воркер, `ab -c 50 -k`,
таблица `bench_rows`):

| операция | Ferrox+asyncpg (Python) | Ferrox+ferrox.db (Rust) |
|---|---|---|
| GET /rows (100 строк) | 8 007 | **14 817** |
| GET /rows (1000 строк) | 1 398 | **5 761** |
| GET /ping | 97 296 | 98 414 |

* Чтение — **×1,85 на 100 строках и ×4,1 на 1000**. Разрыв растёт с числом строк: Python
  упирается в GIL (`Record` + `dict` + Rust-JSON в одном потоке), а запрос, разбор строк и
  JSON целиком идут в Rust на 4 tokio-потоках, GIL отпущен.
* **`prepare_cached`** дал **+38–40 %** на 100 строках (10,3 тыс. → 14,2 тыс.) и нейтрален
  на 1000: подготовка statement — фиксированная цена, а широкий ответ упирается в разбор.
* **`deadpool`** (лимит соединений, recycle-проверка) сам по себе скорость на 1000 строках
  не меняет — это подтверждено A/B: ручной пул на mpsc-канале даёт те же ~5,9 тыс. Сначала
  казалось, что пул просадил 1000 строк (7,7 → 5,8), но повторный A/B в одном билде этого
  не подтвердил (прежние 7,7 тыс. — артефакт замера).
* **Маппинг типов**: int2/4/8, bool, float4/8, text, `NUMERIC` (свой декодер двоичного формата,
  без потери точности), `JSON/JSONB`, `UUID`, `DATE/TIME/TIMESTAMP/TIMESTAMPTZ` (ISO-строки),
  `bytea` (hex), одномерные массивы всех этих типов (`NULL` внутри массива → `null`).
  `NULL` → `null` (раньше паника на nullable-колонке). Параметры: str/int/float/bool/None.
* **TLS**: `?sslmode=disable` — без шифрования (`NoTls`), иначе rustls с системными корневыми
  сертификатами (по умолчанию у Postgres `prefer` — TLS попробуется, при отказе сервера
  произойдёт fallback на plaintext).
* Тесты — `tests/test_ferrox_db.py`, **10 тестов** (пропускаются без доступного PostgreSQL);
  сюита 207 → 217.
* `ferrox.db` — часть единого wheel (maturin mixed); собирается тем же `check.sh`/`build_packages.sh`.

### Самодельный клиент по проводу против asyncpg (`bench/pg_wire.py`, `wire_bench.py`)

Протокол PostgreSQL v3 реализован вручную: startup, SASL/SCRAM-SHA-256, простой запрос,
расширенный (prepared + бинарный формат) и пайплайн. 10 клиентов × 1000 запросов, один процесс:

| Запрос | свой клиент (wire) | asyncpg | разрыв |
|---|---|---|---|
| `SELECT ... LIMIT 1` | 47 919 | 57 778 | −17 % |
| `SELECT ... LIMIT 10` | 27 177 | 53 967 | −50 % |
| `SELECT ... LIMIT 100` | **5 682** | **29 576** | −81 % |
| `LIMIT 100`, 1 клиент | 3 832 | 12 793 | −70 % |
| `LIMIT 100`, 50 клиентов | 5 748 | 24 021 | −76 % |
| `INSERT`, 10 клиентов | 4 138 | 4 243 | −3 % |

* **Цена разбора строк: ≈15,7 мкс на строку у своего клиента против ≈1,7 мкс у asyncpg — в 9 раз.**
  Именно это объясняет весь разрыв: на узких ответах (1 строка) рукописный клиент отстаёт всего
  на 17 %, на широких (100 строк × 3 поля) — в 5 раз. Драйвер покупает не сеть и не протокол,
  а компилируемый разбор результата.
* Проверено и **отброшено** как объяснение: prepared statements + бинарный формат (без выигрыша),
  пайплайн 10/50 запросов (6 133/6 295 против 5 562), `TCP_NODELAY` (без изменений).
  Значит дело не в сервере, не в формате и не в сокете.
* **На записи разницы нет** (4 138 против 4 243): запись упирается в диск, а парсить там нечего.
* Оговорка: `INSERT` у своего клиента идёт с литералами (простой протокол), у asyncpg — с `$1`.

### Прототип тонкого слоя на asyncpg (`ferrox/contrib/rawdb.py`, окт 2026)

Пятая колонка в `bench_postgres.py` — приложение на `RawRepository`/`RawUnitOfWork` из нового
модуля: те же 5 маршрутов, тот же протокол (`ab -c 50 -k`, GET 5000 / POST 3000 / ping 10000),
granian, 1 воркер. Два прогона:

| операция | Ferrox+asyncpg (инлайн) | Ferrox+RawRepo (слой) | Ferrox-Core | Ferrox-ORM | FastAPI |
|---|---|---|---|---|---|
| GET /users | 3 672 / 3 669 | **3 115 / 3 094** | 1 137 / 1 008 | 776 / 746 | 525 / 533 |
| POST /users | 8 414 / 8 713 | **5 234 / 5 522** | 599 / 633 | 685 / 656 | 612 / 611 |
| GET /ping | 84 068 / 91 088 | 90 193 / 90 017 | 87 468 / 87 300 | 88 310 / 78 568 | 24 861 / 23 979 |

* Слой даёт **×2,7–3,1 на чтении и ×8,3–8,7 на записи** относительно SQLAlchemy Core.
* Цена самого слоя — **−18…−19 % к инлайн-сырому драйверу на чтении и −38…−42 % на записи**:
  это транзакция на запрос (`BEGIN` + оператор + `COMMIT`) плюс конструктор репозитория.
* Объём: **97 строк кода** + 134 строки докстрингов, тесты — 131 строка кода, 14 тестов
  (сюита 162 → 176).
* Модуль не заменяет SQLAlchemy целиком: нет миграций, типизированных моделей строк
  (только dict), защиты от N+1 и переносимости на другие СУБД. Фильтры — явный SQL
  (`Condition("age > $1", [18])`), это осознанный размен.
* Тесты сразу поймали реальный дефект: без явного `BEGIN` asyncpg коммитит каждый оператор
  сам, и Unit of Work перестаёт быть единицей работы — `test_unit_of_work_rolls_back_on_error`.

### Декларативные модели поверх rawdb (`ferrox/contrib/rawmodel.py`, окт 2026)

`RawRepository` отдаёт `dict`, поэтому на каждую строку строится словарь. `RawModelRepository`
маппит строку в `slots`-датакласс позиционно (`cls(*row)`) — словаря нет. Замер изолирует
именно маппинг (`bench/micro_bench_model.py`, 1000 строк, лучшее из 200 прогонов, PG 18.6;
µs на строку):

| выборка | tuple | `__init__` (путь репо) | `from_row` (обёртка) | dict |
|---|---|---|---|---|
| `users` (3 поля) | 0.04 | 0.09 | 0.12 | 0.17 |
| wide (10 полей) | 0.08 | 0.18 | 0.21 | 0.34 |

Полный путь `SELECT + маппинг` (µs на строку, 1000 строк в ответе):

| выборка | `RawRepository` (dict) | `RawModelRepository` (модель) |
|---|---|---|
| `users` (3 поля) | 0.40–0.43 | **0.32** |
| wide (10 полей) | 0.80–0.87 | **0.60–0.61** |

* Исходная гипотеза про `dict` подтвердилась: словарь стоит **≈4,4 позиционного кортежа**
  (0.17–0.18 против 0.04 µs). Готовая модель дешевле dict в **×1,85–1,9**.
* **Ускорение (окт 2026).** Было: репозиторий звал `from_row` = classmethod → `cls(*row)`,
  лишний кадр вызова (0.12 / 0.21). Стало: строит модель напрямую (`cls(*row)`, 0.09 / 0.18) —
  это **−25 %** маппинга и **−5…−8 %** полного чтения (0.35 → 0.32, 0.64 → 0.60).
  Отдельно замерено, что выигрыш даёт именно кадр обёртки: `classmethod → cls(*row)` стоит
  ~0.17 против 0.09 у `cls(*row)` напрямую, а сам `object.__new__` ≈ `__init__` — трюка с
  `object.__new__` недостаточно.
* **Identity-map** переведён с `WeakValueDictionary` на обычный dict (живёт один unit of work):
  `put` **0.296 → 0.055 µs/строка**, `get` 0.077 → 0.050. Слабая ссылка на каждую строку
  стоила дороже самого маппинга.
* Выигрыш не «в разы» и не от языка: на широкой выборке узкое место — сам разбор в asyncpg,
  модель убирает только построение словаря и доступ по ключу. Именно эту цену и платит ORM
  поверх драйвера.
* Цена: поля модели должны идти в порядке `SELECT *`; зато атрибуты типизированы, а не
  произвольные ключи. Миграций, связей и защиты от N+1 по-прежнему нет — это тонкий слой.
* Имена таблиц плюрализуются (`User → users`, `Person → people`, `Box → boxes`); override —
  параметром (`select(User, "app_users")`) или атрибутом `__table__` на модели.
* Резерв на будущее: `conn.fetch(sql, record_class=Model)` строит модель прямо в C (маппинг ≈0) —
  замерено **×1,6 на чтении**, но требует модели-наследника `asyncpg.Record` (иммутабельность,
  без defaults/`__table__`-датакласса). Пока не взят.
* Тесты — `tests/test_rawmodel.py`, **25 тестов** (сюита 176 → 207), часть интеграционная на PG.

### HTTP-сравнение фреймворков (`bench/bench_rows.py` + `plot_rows.py`, окт 2026)

Восемь вариантов, 1 / 100 / 1000 строк из PostgreSQL, `ab -c 50 -k`, granian, 1 воркер,
лучшее из 2 (req/s):

| вариант | 1 строка | 100 строк | 1000 строк | /ping |
|---|---|---|---|---|
| ferrox-asyncpg (dict) | **15 540** | 7 849 | 1 275 | 91 935 |
| ferrox-msgspec | 14 611 | **10 664** | **2 279** | 91 642 |
| ferrox-rawmodel | 13 959 | 9 011 | 2 199 | 91 208 |
| litestar-asyncpg (dict) | 12 094 | 6 929 | 1 588 | 36 936 |
| litestar-msgspec | 11 138 | 8 218 | 2 032 | 36 636 |
| litestar-orm | 2 474 | 1 028 | 283 | 37 503 |
| fastapi-orm | 2 072 | 680 | 161 | 24 408 |
| django-orm | 481 | 474 | 417 | 1 784 |

* **Ferrox быстрее Litestar во всём.** `/ping` (чистый фреймворк) — **×2.5**; на строках —
  ×1.1–1.3, потому что там доминирует общая часть (PostgreSQL + asyncpg + msgspec), а не
  роутер. FastAPI — ×3.8 на `/ping` и ×10–14 на строках (сверху ещё SQLAlchemy ORM).
  Django — sync-view под ASGI, упирается в threadpool-обвязку (1 784 на `/ping`).
* **rawmodel теперь ≈ msgspec.** Перевод модели на `msgspec.Struct`, `RawUnitOfWork(readonly=True)`
  (без BEGIN/COMMIT для чтения) и отказ от identity-map на `list()` убрали 2-кратный разрыв;
  осталось ~5–10 % — репозиторий и сборка SQL.
* **Контрольные `dict`-варианты.** На 1 строке dict + ферроксов Rust-JSON (15 540) даже быстрее
  msgspec (14 611): построение `Struct` окупается только на широких выборках; на 1000 строк
  msgspec уже впереди (2 279 против 1 275).
* График — `.venv/bin/python bench/plot_rows.py` → `bench_rows.html` (самодостаточный SVG,
  тёмная тема, подписи значений, офлайн).
* Разложение времени на 1000 строк (in-process): fetch ~437 µs, явная транзакция `BEGIN/COMMIT`
  ~140 µs, identity-map ~53 µs — поэтому read-only путь и отсутствие identity-map на `list()`
  и есть выигрыш rawmodel.

### Go: слои доступа и HTTP-сервис (`bench/go_pg_orm/`, окт 2026)

* **pgx — самый быстрый сырой драйвер из трёх** и уже в один поток почти упирается в потолок:
  40 500 против 43 460 на восьми (asyncpg 32 869, tokio-postgres 25 500).
* **ent быстрее GORM на чтении на треть** в один поток (17 000 против 12 950) и на 19 % на восьми
  (25 800 против 21 697); на записи наоборот — GORM немного впереди (5 000 против 4 520).
* **SeaORM масштабируется лучше обоих Go-ORM** (33 962 против 25 800 у ent и 21 697 у GORM).

  на этом инстансе с 10 клиентами, а не свойство языка.
* В приложении Go и Rust близки: ent 8 487 против GORM 7 488 против SeaORM 10 388 против
  Ferrox+SQLAlchemy ORM 874. Относительно Python разрыв ×9,7 (ent) и ×11,9 (SeaORM).
* На записи с пулом 64 Go лучший из всех: 19 357 против 14 218 у Rust и 7 653 у Ferrox.

**Проверенная и не подтвердившаяся гипотеза.** Я предполагал, что чтение в Go-сервисе упирается
в reflection стандартного `encoding/json`. Добавил переключаемый быстрый энкодер (`--json sonic`)
и прогнал A/B по 3 цикла: **sonic даёт всего +5–7 % (медианы 23 020 против 21 486 при пуле 16),
это в пределах шума ноутбука** — гипотеза не подтвердилась. Значит упор не в кодировщике;
похоже на перемещение данных: 5,3 КБ JSON × 25 тыс. запросов/с ≈ 130 МБ/с тела ответа.

### Профиль пути через базу: куда уходит ~1 мс (`bench/profile_db_path.py`, окт 2026)

Замер in-process (httpx ASGI-транспорт, по одному запросу, без профилировщика),
таблица `users` = 60 тыс. строк, `SELECT ... LIMIT 100`, PG 18.6:

| Вариант | Время запроса | `execute` (круг до базы) | маппинг строк | остаток хендлера |
|---|---|---|---|---|
| `/ping` — без базы | 158 мкс | — | — | — |
| `/asyncpg` — сырой драйвер, совсем без SQLAlchemy | **716 мкс** | 176 | 21 | 87 |
| `/raw` — `text(...)` через SQLAlchemy, без сессии | 949 мкс | 284 | 103 | 100 |
| `/core` — `select(users)` + `mappings()` | 1 146 мкс | 464 | 115 | 149 |
| `/orm` — `select(User)` + объекты модели | 1 299 мкс | 633 | 37 | 205 |

Разброс между прогонами ±10%, поэтому читать надо разницу внутри одной таблицы:

* **цена SQLAlchemy в приложении**: +233 мкс на запрос для `text()` и **+430 мкс** для Core
  относительно сырого драйвера; ORM добавляет ещё +153 мкс — итого **+583 мкс (×1,8 к сырому)**
* в пересчёте на один процесс: ~1 250–1 400 req/s с сырым драйвером, 870–950 с Core и
  ~690–770 с ORM. Сетевые замеры с `ab` дали 932 req/s на воркер для Core — сходится
* то есть «SQLAlchemy медленный» — это про фиксированную стоимость ~0,25–0,45 мс на запрос,
  а не про «в 7 раз»: ×7 относилось к голому драйверу без HTTP, JSON и ASGI
* часть этой стоимости — greenlet-мост (`await_only` / `greenlet_spawn`, в профиле видно как
  `greenlet.switch` ~27 мкс на запрос): цена синхронного API SQLAlchemy внутри asyncio

Что видно по CPU (cProfile, self time, доли; абсолютные мкс поделены на накладные
профилировщика ~×1.7):

| Категория | `/core` | комментарий |
|---|---|---|
| ожидание сокета базы (ядро) | ~25% | круг до PG + сервер — это вся «база» в запросе |
| SQLAlchemy | ~19% | компиляция запроса, обработка результата, greenlet-мост |
| Rust-ядро: json + gzip | ~11% | сборка ответа, прямо измерено ниже |
| asyncio | ~7% | цикл событий |
| наш код (хендлер) | ~5% | `dict(r)`, сборка ответа |
| asyncpg | ~2.5% | протокол |
| Ferrox (Python-слой) | ~1% | сам фреймворк почти бесплатный |

Выводы:
* База как сервер — примерно **десяток процентов** времени запроса; остальное Python-обвязка.
* **ORM дороже Core на ~150 мкс**, и это ровно конструирование сущностей
  (`_instance`, `new_instance`, `_populate_full`, `__get__`) — видно в профиле.
* **`text()` без сессии быстрее Core на ~165 мкс** и ORM на ~315 мкс — там, где модель
  не нужна, ORM/Core-select только мешает.
* Сборка ответа в ядре — прямой микрозамер (`bench/micro_bench_response.py`, ответ из 100
  строк = 5,3 КБ): **JSON 119 мкс** + **gzip 87 мкс** (сжатие ×6,8) = ~⅕ времени запроса.
* `ab` по умолчанию **не** отправляет `Accept-Encoding`, поэтому сетевые числа идут без gzip,
  а браузер и httpx его просят. Поймать эффект gzip на сетевых замерах не получилось: на 50
  клиентах разброс между прогонами ±20% (766 / 1115 / 994 против 1203 / 1200 / 1037 req/s) —
  эффект тонет в шуме, поэтому его стоимость приводится прямым микрозамером, а не сетевым.

Запуск: `.venv/bin/python bench/profile_db_path.py --requests 400`.

Микро-замер JSON (окт 2026): Rust-писатель быстрее **только** на плоском мелком dict (×1.34),
на вложенных ответах `json.dumps` выигрывает (×0.45 на 1 объекте, ×0.24 на 200). Поэтому
скорость Ferrox доказывается сетевыми замерами с `ab`, а не микрозамерами сериализации.

## legacy_httpx/ — что здесь и почему не годится

`bench_network.py`, `bench_payload.py`, `bench_modes.py`, `bench_full.py`, `bench_real.py`
и их helper-приложения. Они ходят httpx-клиентом, поэтому их req/s **client-bound** —
их диапазон 3–7k req/s отражает клиент, а не сервер. Пригодны, чтобы посмотреть ASGI-путь
без сети (`bench_real.py`) или сравнить режимы uvicorn, но не для цифр в README.

## Helper-приложения (`_`-префикс)

`_bench_db_*.py`, `_bench_dbvar_*.py`, `_bench_pool_*.py`, `_bench_pg_*.py` — минимальные
приложения для БД-замеров. Имена собираются динамически (`f"_bench_pool_{name}.py"`), поэтому
поиск по имени их «не находит» — на самом деле их запускают основные скрипты как отдельные
серверы. Не удаляй, не проверив `bench_*.py`. `_bench_db_post.json` и `_bench_pg_post.json` —
тело POST-запроса для замеров вставки.

`_abgen_*.py` — приложения, которые генерирует `ab_bench.py` при каждом запуске (в git не идут).

## Протокол замера (иначе цифры не сравнимы между сессиями)

1. **Погасить фоновые потребители CPU**: `ollama` (llama-server ест ~17% ядра), `qdrant`,
   `searxng`, браузер. Пример: `curl -X POST :11435/api/generate -d '{"model":"...","keep_alive":0}'`.
2. Проверить, что машина простаивает: `uptime` (load average) и `ps -eo pcpu,comm --sort=-pcpu | head`.
3. Только после этого запускать `./bench/run_all_ab.sh` — он пишет дату, число ядер, load и версию
   `ab` в шапку `RESULTS_ab.txt`. Без этих метаданных цифры двух прогонов сравнивать нельзя.
4. Сравнивать **соотношения** (Ferrox/FastAPI), а не абсолютные req/s из разных сессий: одна и та же
   машина даёт ±2–3% дрейфа от частоты CPU и фона, а на граничных сценариях и больше.

Требования: окружение `.venv` в корне репозитория, `ab` (`apt install apache2-utils`),
Docker с контейнером `ferrox-pg` на :5432 — только для `bench_postgres.py`.
